# Midscene.js Chrome 插件集成 — 产品提案 (PRD)

> **状态**: 待评审 | **创建日期**: 2026-05-21 | **版本**: v1

---

## 1. 问题陈述

当前智能测试中台的执行模式是"用户输入 NLP → 生成 YAML → execute-service 用 Playwright + Midscene Agent 自动执行"。这个流程有一个根本性障碍：**execute-service 无法登录需要人机交互的目标网站**（SSO 单点登录、MFA 多因素认证、验证码、企业内网 VPN 登录等）。

用户手上已经有了 Midscene.js v1.52 Chrome 扩展，该扩展可以在用户本地浏览器中录制操作、生成测试步骤。但目前扩展和中台是两个孤岛——扩展导出的用例无法流入中台，中台的调度执行能力也无法被扩展用户使用。

### 痛点证据
- 企业测试场景中，70%+ 的目标系统有 SSO/验证码等登录门槛
- 用户需要重复"手动登录 → 录制 → 手动整理成 YAML → 贴到中台"的繁琐流程
- 扩展导出的测试步骤没有持久化存储和团队共享能力
- 中台的批量执行、定时执行、报告管理等能力对"手动录制"的用户不可达

## 2. 目标

| # | 目标 | 类型 | 衡量标准 |
|---|------|------|----------|
| G1 | 用户可在自己浏览器登录目标网站后，通过插件录制/编写测试步骤并一键导入到中台 | 用户目标 | 导入成功率 > 95%，操作步骤 ≤ 3 步 |
| G2 | 所有中台用户都能获取和安装该插件 | 平台目标 | 插件中心页面 UV 达到活跃用户的 50% |
| G3 | 导入的测试用例可在中台被查看、编辑、执行，与平台原生用例体验一致 | 用户目标 | 导入用例的执行成功率与原生用例持平 |
| G4 | 建立"插件录制 → 中台管理 → 批量执行"的协作链路 | 平台目标 | 上线后 30 天内至少 10 个活跃用户使用导入功能 |

---

## 3. 非目标 (Non-Goals)

| # | 非目标 | 原因 |
|---|--------|------|
| N1 | 插件导出 Cookie/Session 让 execute-service 免登执行 | v1 范围过大，先解决"录制→导入"链路；v2 再考虑 |
| N2 | 插件实时同步（边录制边推送到平台） | 增加复杂度，导出按钮即可满足 MVP |
| N3 | 发布到 Chrome Web Store | 企业内网场景，开发者模式加载足够；后续可评估 |
| N4 | 支持 Firefox / Edge 等其他浏览器 | 当前插件仅支持 Chrome Manifest V3 |
| N5 | 在插件中嵌入完整平台前端 | 违背"插件轻量化"原则，保持插件专注于测试操作 |

## 5. 需求分类

### Must-Have (P0)

| # | 需求 | 说明 |
|---|------|------|
| R1 | **插件中心页面** | 前端新页面 `/plugin-center`，含下载、安装指南、已导入用例列表 |
| R2 | **扩展包托管控下载** | platform-service 提供 `GET /api/plugin/extension/download`，返回 Midscene .zip |
| R3 | **插件导出桥接模块** | 在扩展中新增 `platform-bridge.js`，将测试步骤序列化并 POST 到中台 |
| R4 | **后端导入 API** | `POST /api/plugin/test-cases/import`，解析步骤、生成 YAML、存为 TestCase |
| R5 | **用例来源标识** | 区分"平台创建"和"插件导入"的用例，便于溯源和管理 |

### Nice-to-Have (P1)

| # | 需求 |
|---|------|
| R6 | 导入用例时支持选择已有项目或新建项目 |
| R7 | 插件可配置中台地址和 Token（支持多环境） |
| R8 | 导入历史记录（谁、何时、导入了哪个用例） |

### Future (P2)

| # | 需求 |
|---|------|
| R9 | 导入时携带 Cookie/Session 数据 |
| R10 | 插件版本检测与自动更新提示 |
| R11 | 支持批量导入多个用例 |
